# Void review (before unblinding)

Scope: candidates S16, X2, X4, X10 and A6, all from round r2 for both builds (harness 4a895ba4d9c6; r1's fix-harness note moved it there from 00dcf74bd482).
Read: SPEC.md, GRADER.md, results/build-{1,2}/r2/results.jsonl and logs/{S16,X2,X4,X10,A6}.log, notes/adjudicate-*-r2.md, notes/judge-*-2.md, notes/fix-harness-r1.md, notes/run-*-r2.md and notes/prep.md.
Nothing was re-run, the VM was not touched and no build source was read. Token-shaped strings were redacted while reading. No secrets are recorded here.

| Check | Decision | Why |
|---|---|---|
| S16 | VOID (both) | Both builds: 39/39 graded cells are 403 with controls (approve, reject, members, grants, tokens, audit, audit/verify; T_dev_r, T_dev_rw, T_prod_rw). The only open cell, logged as HARNESS ERROR "review, not graded" on both, is POST /auth/token sent with a service-token bearer **and a human's valid email and password**. Build-1 returns 200 + PAT and build-2 201 + PAT. SPEC 7.2/§4 make /auth/token the unauthenticated credential login, and the PAT comes from the password, not the token. The same request without the bearer gives the same PAT (control "valid login without bearer"). So the cell does not test SPEC 2.7 ("service tokens can never ... create PATs"), and its expectation conflicts with the route SPEC defines. The decisive probe (service-token bearer alone or with bad creds, expect no PAT) was never run. The check as built cannot give a SPEC-grounded verdict. Harness fix for a re-run: score a bearer-only probe and log the bearer+creds case as info. |
| X2 | VOID (both) | Both builds behave the same. 3 transplants (other key, other env, acme->globex) were verified. 9/9 tampered reads (get, get v1, export) returned 500 with a generic JSON error and **no value**. The source was still readable, and the destination read its own value again after restore (10 ok asserts and controls on each). The only failing assert is "want a 4xx, not 5xx". GRADER X2 asks that "each read must error; returning any value = fail", and both meet that. The 4xx demand comes only from the global "any 500 = fail" line. SPEC's status table (400/401/403/404/409/413/429) has no code for an authenticated, valid request that hits data an operator corrupted in the DB. Every 4xx there means a client fault, so the honest status is 5xx. The check demands a status that SPEC's semantics don't support. Harness fix: for fault-injected reads, pass a clean 5xx with a generic error body and no value. |
| X4 | STANDS | Not a both-arm fail. Build-2 passes: with MASTER=old alone, /readyz stayed 503 (refuse), and rotation and new-key-alone worked. Build-1: rotation re-wrapped 14 data keys, and new-key-alone read 7/7. With old-key-alone the server reported ready and 7 reads returned 500 internal_error with no value. Read together, GRADER X4 "fails closed (refuses or errors), never garbage" and "any 500 = fail" mean refuse or a non-5xx error. That can be met under SPEC: §4 rotation ties data-key unwrapping to "before the server reports ready", and build-2 shows it. Each build's result stays as reported. |
| X10 | STANDS | Both builds were evaluated with the same 665 probes and 48 controls. Some sub-asserts are harness artefacts: the raw unescaped `;` "DROP" query variants make the server ignore the filter and return the caller's own data (7 asserts on each build), and the "unrequested own-tenant data" export hit is the caller's own export. Each build still has valid failures without them. Build-1 has 39 hard 500s on NUL input (path params, audit actor/action query, JSON email/project/env fields), which GRADER X10 and "any 500" forbid. Both builds also have 4 accepted homoglyph/fullwidth emails (201). GRADER X10 lists homoglyphs in every JSON field, SPEC is silent on email format, and rejecting them is possible and does not contradict SPEC. The fails are kept. Harness should still fix the raw `;` variants. |
| A6 | VOID (both) | Both builds detect the mid-chain delete: verify rc 9 and valid:false from the API, CLI and CLI --json. Each is valid before the delete and valid again after re-insert. Both report first_invalid_seq = the **deleted** seq (2628 / 3032), and GRADER wants the next seq (2629 / 3033). SPEC §4 says only "reports the first invalid sequence number". After a delete, the missing seq k (the gap) and k+1 (the broken prev_hash link) both fit that wording. GRADER's k+1 is a choice that SPEC does not imply, and two independent builds both took the other reading. The fault is in the spec/check's expected value. Fix: accept {k, k+1}. |

Result: void for both builds: S16, X2, A6. Stand as reported: X4, X10. No candidate was marked not-evaluated: every one ran to completion on both arms with controls, and its log separates build behaviour from harness or host failure.
