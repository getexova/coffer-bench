# Design decisions

This file lists every point where SPEC.md is silent or leaves a choice. Each entry
gives the decision and a short reason. The detailed design is in
[CONTRACT.md](CONTRACT.md). Numbers are stable, because other documents refer to them
as "DECISIONS N". Entries 1–60 are the original design, corrected where the code has
since changed. Later entries are grouped by area.

## Platform and stack

1. **Go with standard-library `net/http`, plus `pgx/v5` and `x/crypto`; the CLI uses only the standard library.** This keeps the set of dependencies to audit small, and each of the server and CLI is one static binary.
2. **PostgreSQL 16 is the only state store.** SPEC requires `postgres:16`. Transactions and row locks give gap-free versions and serialised audit appends with no extra infrastructure.
3. **Migrations are embedded SQL, applied at boot under `pg_advisory_lock(7420001)`, each file in its own transaction, and recorded in `schema_migrations`.** They are idempotent and safe when two servers start at once.
4. **An ID is a type prefix plus 20 random bytes in lowercase base32** (`usr_`, `org_`, `prj_`, `env_`, `tok_`, `chg_`). IDs are opaque, can't be guessed, and are easy to read in logs. Nothing is numbered in sequence, so nothing can be enumerated.

## Tenancy and authorization

5. **Emails are unique across all orgs (matched on `lower(trim(email))`).** SPEC puts every user in exactly one org, and login takes only email and password, so the email alone must identify the user. The cost: a 409 on member add or org create reveals that the email exists in *some* org (see SECURITY.md).
6. **The platform admin is a user with role `platform_admin` and no org** (a CHECK enforces: platform admin if and only if `org_id IS NULL`). Every org-scoped route returns 404 for it, so it can never read tenant data, not even by accident.
7. **Platform routes (`/admin/...`) return 404, not 403, to everyone except the platform admin.** Org users should not learn that the admin surface exists, which matches "invisible means 404".
8. **Authorization resolves in a fixed order:** platform-admin check (404); slug syntax (404); project in the caller's org (404); access to the project (404); env (404); permission (403); key syntax (400); secret or version (404). This way, neither a validation error nor a 403 can reveal whether an invisible resource exists.
9. **A service token calling `GET`/`POST /projects/{p}/envs` gets 403 for its own project and 404 for any other.** It can see its own project but has no permission on its metadata. Other projects stay invisible.
10. **Grants apply only to role `member` (otherwise 400), and nobody can grant to or revoke from themself (403).** Owners and admins already have access to every project, and this closes off self-escalation.
11. **Changing your own role is always 403, except that the last owner demoting themself gets 409.** This follows "no self-escalation" and still gives a precise last-owner signal. Removing yourself works the same way.
12. **Removing a member deletes their PATs and grants; service tokens they created keep working.** Service tokens belong to the org, so CI shouldn't break when an employee leaves. They can be revoked explicitly. Pending changes proposed by the removed user can no longer be approved (decision 65).
13. **Members see only the change requests they proposed, and only in projects where they still hold a grant; owners and admins see every change.** Members can't approve, but they can track their own proposals without seeing projects they lost access to. Lists are newest first, at most 1000 entries.
14. **The two-person rule compares the approver with both the proposing actor (`proposed_by`) and the person behind it (`proposed_by_user`, which is a service token's creator).** An admin can't approve a change they pushed through their own service token.
15. **Rejecting a change is not subject to the two-person rule.** A proposer who is an owner or admin may withdraw their own change. That is harmless.
16. **Disabling an org is idempotent (200), and its users and tokens get 401 on their next request.** Users of a disabled org are treated as unauthenticated, so the status doesn't reveal the org's state. Logging in with the correct password returns the same 401 as a wrong password and counts as a failed attempt.

## Secrets

17. **`expected_version` refers to the head version, counting tombstones; `0` means "has never existed".** This keeps optimistic concurrency unambiguous across delete and re-create.
18. **Deleting a key that is absent or already deleted returns 404.** This avoids piling up tombstones and matches "get returns 404".
19. **Rollback is allowed onto a deleted head, but the target must not be a tombstone.** Restoring a deleted secret is the main reason to roll back.
20. **In a protected env, set/delete/rollback check existence (404) and `expected_version` (409) when the change request is created. Approval checks again: the head must still be at `base_version` (otherwise 409 and the request becomes `stale`), and the proposer must still be allowed to write (decision 65).** The proposer finds out early, and applying the change is still safe.
21. **A pending change's value is encrypted with an AAD scoped to the change id, then re-encrypted under the secret AAD when approved. Approved, rejected and stale changes have their pending ciphertext set to NULL.** No plaintext is at rest even for pending writes, a pending ciphertext can't be swapped into a secret row, and decided changes keep no value.
22. **Reads (get, get version, export) commit their audit events before the value is returned. If the audit append fails, the response is 500 and contains no value.** "Every value exit is audited" holds even when the DB fails.
23. **Export with a `format` other than `json` or `dotenv` returns 400; the default is `json`.** The CLI's `secrets export` also defaults to `json`.

## Crypto and authentication

24. **AES-256-GCM everywhere, in the format `0x01 || nonce(12) || ciphertext||tag`, with random nonces.** It is the standard-library AEAD, and the version byte allows a future change of algorithm. The volume encrypted under each project DEK stays far below GCM's random-nonce limits.
25. **AAD strings are versioned and separated by purpose (`coffer/dek/v1`, `coffer/secret/v1`, `coffer/change/v1`, `coffer/canary/v1`).** A ciphertext made for one purpose can't be reused for another.
26. **A canary (32 random bytes) wrapped under the master key detects a key mismatch and drives rotation.** A wrong key fails at boot, instead of producing new data nobody can decrypt. On a database that has no canary yet, the server refuses to start unless every existing DEK unwraps with the current key. The canary plaintext also seeds the app-role password (decision 64).
27. **Rotation re-wraps only the DEKs, in one transaction, and skips rows already under the new key.** It is idempotent and fast, and values don't need re-encrypting when the master key rotates. Restarting with `PREVIOUS` still set finishes any rows that were only partly rotated.
28. **The placeholder master key is rejected by exact string comparison (it isn't 32 bytes when decoded, so it would fail the length check as well).** This protects against copying `.env.example` as is.
29. **argon2id with t=2, m=64 MiB (configurable, 19456 KiB to 4 GiB), p=2, at most 4 hashes at a time.** These are the OWASP-recommended parameters, and the semaphore bounds memory use during a login flood. After a successful login, a hash made with different parameters is upgraded (decision 69).
30. **Lockout is keyed by normalized email, unknown emails included (a malformed email gets the bucket `invalid:email:<hash>`): 5 failures in a sliding 15-minute window, checked before the password.** It stops guessing and treats known and unknown emails the same. A locked attempt returns 429, is audited as `auth.login` with result `denied` and reason `locked`, and does not count as a new failure. A wrong current password on `POST /auth/password` counts toward the same lockout. Attempts for one email are serialised with `pg_advisory_xact_lock`.
31. **A token is 32 random bytes in base64url with the prefix `cof_pat_` or `cof_st_`, stored as SHA-256.** That is 256 bits. A fast hash is fine for tokens with that much entropy, and the prefixes make secret scanning possible.
32. **PATs last 30 days by default (`COFFER_PAT_TTL`, a Go duration between 1m and 8760h).**
33. **No authentication state is cached; one query per request joins the token with its user, org, project and env.** That makes revocation immediate by design.
34. **A service token cannot call `POST /auth/token`, `POST /auth/logout` or `POST /auth/password` (403).** Any other Authorization header on `POST /auth/token` is ignored, and the request is handled as a normal login.
35. **`COFFER_REQUIRE_PASSWORD_CHANGE` (P1) defaults to `false`.** Users created with an initial password (org owners and added members) are always stored with `must_change_password=true`, but it is reported and enforced only when the flag is `true`. When enforced, every route except `POST /auth/password`, `POST /auth/logout` and `GET /me` returns 403 `password_change_required`, and the denial is audited. The bootstrap admin is never forced. The default keeps the documented quickstart working (an admin-created owner logs in and works at once).

## HTTP

36. **The body limit is enforced in middleware for every route, before routing (413).** Routes that take no body (logout, approve, reject, org disable) accept an empty one. The "missing body is 400" rule applies only to routes that expect a body.
37. **Strict JSON: unknown fields, trailing data, a non-object body, invalid UTF-8 and lone surrogate escapes are 400. Duplicate keys are allowed (the last one wins).** Rejecting unknown fields is how "fields a caller may not set" get rejected rather than ignored.
38. **Extra hardening headers: `Referrer-Policy: no-referrer`, `X-Frame-Options: DENY`, `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'`.** They are sent on every response the handler writes, including 404s outside `/api/v1`.
39. **No CORS headers are ever sent. `OPTIONS` goes through normal routing (404, or 405 with `Allow`). `OPTIONS *` and any request target that doesn't start with `/` get the JSON 404.** No origin gets CORS access, and every response looks the same.
40. **An incoming `X-Request-Id` is ignored; the server always generates its own (16 random bytes, in hex).** This prevents log injection and forged correlation ids.
41. **`X-Forwarded-For` is trusted only when `COFFER_TRUST_PROXY=true`, and then only its first entry, if that entry parses as an IP.** By default, audit source IPs can't be spoofed.
42. **`/readyz` is 200 only when boot has finished, a `SELECT 1` succeeds within 2 s, and every embedded migration is recorded in `schema_migrations` of the database behind the pool. A passing migration check is cached for 1 s.** The check runs on every call, so readiness recovers by itself after a DB outage, and a database replaced under a running server isn't reported ready.

## Audit

43. **Every 403 or 404 from authorization is audited as `authz.denied` (details `{status}`), including a genuinely missing resource under an authorized caller. The target is the route pattern plus the raw identifiers.** The log says no more about existence than the response does. 401s and unmatched-route 404s are not audited, except for login.
44. **Failed and locked logins go to the platform chain with actor `anonymous`, no `org_id`, and target `email:<first 16 hex of SHA-256(normalized email)>`, whether or not the email exists. If the email belongs to an org user, a copy also goes to that org's chain with target = user id. Successful logins go only to the user's own chain.** SPEC routes unauthenticated callers' events to the platform log, and the platform admin must not learn an org's members from it (SPEC §1), so the platform copy looks the same for known and unknown emails. The org's admins still see attacks on their users. The platform chain is always written first, so the lock order is fixed.
45. **`org.create` is written to the platform chain and to the new org's chain, as its first ("genesis") event.** The org's log starts with its own creation. This exposes the platform admin's opaque user id to that org's owners and admins, which is accepted.
46. **Canonical JSON for hashing uses a fixed set of keys, sorted, with no whitespace and no HTML escaping, microsecond UTC timestamps, and `details` holding only strings, integers, booleans and nested objects.** The result is the same in every implementation.
47. **The request pool uses a separate `coffer_app` role without UPDATE, DELETE or TRUNCATE on `audit_events`, and blocking triggers sit on top (P1).** If setting up the role fails, the server falls back to the owner connection and logs a warning. Details are in decisions 64 and 71.

## Operations

48. **The `db` image is written as `docker.io/library/postgres:16`** (the full form of `postgres:16`). Podman's default `short-name-mode = "enforcing"` can't resolve a bare short name without a TTY when the image isn't already present, which would break `up.sh` on a clean machine. Docker resolves both forms the same way.
49. **The `db` service gets only `POSTGRES_USER`/`POSTGRES_PASSWORD`/`POSTGRES_DB` (interpolated from `.env`), not the whole `.env` through `env_file`.** The database container never sees the master key or the admin password.
50. **Server container hardening: distroless static nonroot (65532:65532), `read_only: true` with a 16 MB `/tmp` tmpfs, `cap_drop: [ALL]`, `no-new-privileges`, and a port published on `127.0.0.1` only.** The `db` container gets `no-new-privileges` but not `cap_drop: ALL`, because the postgres entrypoint needs SETUID, SETGID and CHOWN to switch to the `postgres` user. The `db` container publishes no port.
51. **The healthcheck (`/coffer-server healthcheck`, which GETs `/readyz` on the local listener) is defined in both the Dockerfile and `compose.yaml`.** Podman builds OCI-format images by default, and those drop the Dockerfile `HEALTHCHECK`. The compose definition works on both runtimes.
52. **`compose.yaml` makes `server` depend on `db` being healthy, and `up.sh` also starts `db` first, waits for `pg_isready`, and only then starts `server` with `--no-deps`.** The server also retries the DB connection itself, so it doesn't depend on start order.
53. **Scripts never `source` `.env`; values are read with `grep`.** A malformed `.env` can't execute code, and compose reads it as data. A `COFFER_PORT` set in the shell overrides `.env`, as it does in compose.
54. **`init-env.sh` won't overwrite `.env` without `--force`. It writes through a 0600 temp file and a rename, and generates URL-safe passwords (32 characters, about 190 bits).** URL-safe passwords survive `.env` parsing, shell pipelines and URLs without quoting. `openssl rand` is used when present, and `/dev/urandom` otherwise. `--force` on an existing volume warns that the volume keeps the old Postgres password and master key.
55. **`up.sh` creates `.env` with `init-env.sh` when it is missing, starts `db`, waits for it, then always runs `compose up -d --build --force-recreate --no-deps server`, waits for `/readyz`, and builds the CLI with `build.sh`. `restore.sh` restarts the server the same way.** podman-compose (also behind `docker compose` and `podman compose` on podman hosts) doesn't hash `env_file` contents, so without the forced recreate an edited `.env` (rotation, PAT TTL) would silently not apply. The db container and volume are kept, and the server restarts on every `up.sh`. The 180 s readiness timeout (`COFFER_READY_TIMEOUT`) starts after the build and start return, so image build time isn't counted. On failure, the last server logs are printed.
56. **`down.sh` never removes volumes.** Data survives `down.sh` followed by `up.sh`.
57. **Backups are `pg_dump -Fc` taken inside the db container and written through a 0600 temp file. `restore.sh` validates the `PGDMP` signature, then restores into a scratch database (`coffer_restore_incoming`) with `pg_restore --no-owner --no-privileges --single-transaction --exit-on-error` while the server keeps running. Only after that succeeds does it stop the server and swap the scratch database in by rename, in one transaction. If the server is not ready on the restored data (for example the master key doesn't match), it swaps back and fails with `rolled back`.** A truncated or corrupt backup, or the wrong master key, never destroys the live data. Grants for the app role are re-applied at every boot, so `--no-privileges` is safe.
58. **Base images are pinned by version and multi-arch index digest (`golang:1.26.10-alpine3.24@sha256:a201…`, `distroless/static-debian12:nonroot@sha256:afa5…`). `build.sh`, `test.sh` and the Dockerfile use the same Go image; `postgres:16` is kept as SPEC §5 prescribes.** `build.sh` uses a local Go >= 1.26 if one is installed, and otherwise builds in that image and streams the binary out with `tar` (so file ownership is right under both rootless podman and rootful docker). Builds use `-trimpath -buildvcs=false` (the alpine image has no git).
59. **`test.sh` starts a throwaway `postgres:16` on a random loopback port when `COFFER_TEST_DATABASE_URL` is unset, and always removes it on exit. It runs gofmt, `go vet` and `go test -race`, and drops `-race` (with a warning) only when no C compiler exists.** In the container toolchain it installs `build-base` on the fly so `-race` works. With `COFFER_E2E=1` it also builds the CLI and runs `go test -tags e2e ./test/e2e/...` against the running stack.
60. **CI uses node24 action majors (checkout@v7, setup-go@v7, golangci-lint-action@v9, upload-artifact@v7) and pins tool versions (golangci-lint v2.15.0, govulncheck v1.9.0). It lints with gofmt, vet, `go mod verify`, golangci-lint, govulncheck, shellcheck and `check-env-docs.sh`, then tests, builds, and runs a quickstart/e2e and ops-smoke job.** The lint config turns off errcheck for tests and `pgx.Tx.Rollback`, and gosec G115 (integer-conversion noise) and G407 (false positive on the random nonce). The remaining errcheck and gosec exclusions are narrow path+rule+source rules, each with a reason in `.golangci.yml`.

## Later additions: authorization and data

61. **Changing a member's role to `admin` or `owner` deletes all of their project grants, so a later demotion to `member` starts with none.** Grants only mean something for members (decision 10). Keeping them dormant would silently restore old access on demotion, which the admin doing the demotion wouldn't expect, so that admin re-grants explicitly. The role change is audited as `member.role_change` (`{from,to}`). The dropped grants are not audited one by one.
62. **`coffer run` won't start the child (exit 1, nothing executed) if any secret value contains a NUL byte (U+0000), or a key can't be an environment variable name.** SPEC §3 allows NUL in values, and the server stores, returns and exports them exactly. POSIX environment strings end at NUL, though, so such a value can't be passed to a child process without being cut short. Failing loudly is better than silently injecting a truncated value. The message names the key, never the value. Use `secrets get` or `secrets export --format json` for such values.
63. **The README quickstart counts from nothing: `git clone` and `cd` included, one command per line, no `&&`, 10 commands to `secrets get`.** `up.sh` creates `.env` (through `init-env.sh`) when it is missing and builds the CLI (through `build.sh`) once the server is ready, so neither needs its own quickstart line. `<REPO_URL>` is a placeholder, because the repository has no fixed public URL. `COFFER_SKIP_CLI_BUILD=1` skips the CLI build in `up.sh`.
64. **The restricted DB role's password is HMAC-SHA256(database canary, role and database name), and it is sent to Postgres as a SCRAM-SHA-256 verifier computed by the client.** The canary is random per database and survives master-key rotation, backup and restore, so every boot sets the same password. A second server, or a boot that is refused, never breaks the connections of a running server. The plaintext password never reaches Postgres or its logs. The role name (`coffer_app`) can't be configured; tests change it per database.
65. **Approving a change re-checks its proposer inside the approval transaction, with row locks. A user must still be in the org and be an owner or admin, or a member with a writer grant on the project. A token must be a service token that isn't revoked or expired, has read-write access, and is scoped to the change's project and env.** If the check fails, the change becomes `stale` (with `decided_by`/`decided_at` set), `change.stale` is audited with result `failed` and reason `proposer_unauthorized`, and the call returns 409. Pending changes are not marked stale automatically when access is removed; the check happens at approval. Revocation is immediate (SPEC §2.11), so a change is applied only on behalf of a proposer who could still make the write.
66. **`change.stale` is audited with result `failed` (with `base_version`, and `reason` when the proposer lost access).** A stale change was decided but not applied.
67. **Decryption failures (a tampered or swapped ciphertext) are audited as `failed` with reason `integrity` before the 500, under action `secret.read` (get, get version, export), `secret.rollback` (reading the target version), or `change.approve` (the pending value or the rollback target).** An attempted value exit that fails is still recorded. The event is appended after the transaction rolls back, on a context the client can't cancel.
68. **Login, password change and logout finish their DB work (failure counter, audit, revocation) on a context the client can't cancel (10 s timeout).** Login first waits for a hashing slot on the request context, so a client that leaves while queued has made no attempt. Once the attempt starts, a disconnect can't skip the lockout counter or the audit event.
69. **After a successful login, if the stored hash uses different Argon2 settings from the current ones, the password is rehashed and saved in the same transaction. Failed logins never rehash.** Known accounts then verify at the same cost as the dummy hash used for unknown emails.
70. **Expired `login_failures` rows are deleted for the attempted email on every attempt, and for all emails at most once a minute, in the background.** Unauthenticated callers can't make the table grow without limit.
71. **Schema extras beyond SPEC:** CHECKs (platform admin if and only if `org_id IS NULL`; the column shapes of PATs and service tokens; a version is deleted if and only if its ciphertext is NULL); FKs `secret_versions(env_id,key)` → `secrets` and `tokens.project_id/env_id`; indexes on `users(org_id)`, `tokens(org_id,kind)`, `tokens(user_id)` and `change_requests(org_id,created_at)`. The app role can only SELECT `schema_migrations` and `master_key_check`, has no TRUNCATE anywhere, and a statement-level `BEFORE TRUNCATE` trigger also protects `audit_events`. Migrations, the key check and rotation, and bootstrap run on the owner pool, which is closed before ready (unless the server fell back to it).
72. **The bootstrap admin password is checked against the policy (at least 12 characters, at most 1024 bytes, valid UTF-8, no NUL) on every boot, and an invalid one is a config error (exit 1).** Bootstrapping happens only while `users` is empty, under an advisory lock, and is audited as `platform.bootstrap`.
73. **`COFFER_PORT` is not read by the server.** It is the host port compose publishes, and the container always listens on `:8420` (`COFFER_LISTEN_ADDR`). The server requires `COFFER_MASTER_KEY`, `COFFER_BOOTSTRAP_ADMIN_EMAIL`, `COFFER_BOOTSTRAP_ADMIN_PASSWORD`, and `POSTGRES_USER`/`POSTGRES_PASSWORD`/`POSTGRES_DB` unless `COFFER_DATABASE_URL` is set. The optional `POSTGRES_SSLMODE` (default `disable`) is added to the DSN it builds.
74. **Keys in list and export are ordered with `COLLATE "C"` (byte order), and export also sorts in Go.** Order is deterministic whatever the database locale. Org lists are sorted by slug, members by email, projects and envs by slug, tokens newest first, and changes newest first.
75. **Standalone audit events (reads and denials) go through a per-chain group commit. Each request still waits for its own commit.** This gives throughput under concurrent reads without weakening decision 22. The audit `ts` is taken after the chain lock, so timestamps never go backwards within a chain.
76. **Audit strings are sanitised before hashing and storage: invalid UTF-8 is replaced, NUL is removed, and each field is capped at 2048 bytes.** Postgres `text` and `jsonb` can't hold NUL, and the hash has to match what is stored.
77. **A malformed slug or id in a path returns 404 (audited) before any SQL runs.** NUL and invalid UTF-8 never reach a query, and nothing about existence is revealed.
78. **Login with a malformed email gets the same 401 and a dummy argon2 verify.** Unknown and malformed emails look the same from outside.
79. **The login response is `{token, expires_at, user:{id,email,role,org_id,org_slug,must_change_password}}`, and the `auth.login` success event records `token_id`.** The CLI never stores or prints anything beyond the token itself.
80. **On `POST /auth/password`, a wrong current password returns 403 and counts toward lockout, a locked account gets 429, and a new password equal to the current one gets 400. Success revokes the user's other PATs and clears `must_change_password`.**
81. **`POST /tokens` validates the body (400) before resolving project and env (404). Token names are at most 100 characters and may not contain control characters. `DELETE /tokens/{id}` revokes only service tokens (PATs get 404 there) and is idempotent.**
82. **Integer fields (`to`, `expected_version`, `ttl_seconds`) must be plain JSON integers: no quoted numbers, fractions or exponents (400). Versions that can't exist (0, larger than int32, rollback `to < 1`) return 404, not 400.** A version that is well formed but impossible is simply "not found".
83. **`GET /changes` returns at most 1000 entries; `GET /audit` and `GET /admin/audit` return at most 1000 per call (default 100), newest first.** These bound the size of responses.
84. **If appending the audit event for a denial fails, the server still returns the 403 or 404 and logs the failure.** A broken audit path must not turn denials into 500s, which would let a caller tell them apart. Value reads, by contrast, fail closed (decision 22).

## Later additions: CLI

85. **Echo is turned off with a TCGETS/TCSETS ioctl rather than `stty -echo`, and TTY detection uses TCGETS on Linux (other platforms fall back to `ModeCharDevice`).** No external program is needed, and `/dev/null` isn't mistaken for a terminal. This is best effort: Ctrl-C at the prompt restores echo and exits 130.
86. **Known flags may appear anywhere, also before the command words (`coffer -p x secrets list`), in `--flag value` or `--flag=value` form; a command still rejects flags it doesn't accept (exit 2).** Global flags work in any position.
87. **`run` stops parsing flags at the first positional argument, so `--` is optional; flags after COMMAND go to the child. The command is looked up with the CLI's own `PATH`, not a `PATH` secret. Exit 127 if the command isn't found, 126 if it can't be executed. SIGINT, SIGTERM, SIGHUP and SIGQUIT are forwarded. `--json` has no effect on `run`, because the child owns stdout.**
88. **`secrets delete` and `secrets rollback` also accept `--expect-version N` (sent as query parameter `expected_version` for delete, and in the body for rollback).** This gives the same optimistic concurrency as `set`.
89. **The CLI rejects bad input locally, before sending any request:** a non-integer `--version`, `--expect-version` or `--to` (exit 6); a malformed `--ttl` or one outside 1m..90d (exit 6); an empty, `.` or `..` key, slug or id (exit 6, because the router would otherwise rewrite the path); a value over 65,536 bytes or not valid UTF-8 (exit 6); a password over 1024 bytes or not valid UTF-8 (exit 6); an empty password line (exit 2, so it never counts toward lockout). `--limit`, `--since`, `--status` and `--format` are passed to the server, whose 400 maps to exit 6. Every other path segment is escaped.
90. **With no token at all, the CLI exits 3 without sending a request. A `COFFER_TOKEN` that is set but empty still counts as set (no config file is touched) and exits 3. Whitespace around `COFFER_TOKEN` is trimmed, and a token containing spaces or control characters exits 3 locally, so it never appears in an error message.**
91. **When `COFFER_TOKEN` is set, the config file's `url` isn't read either, because no config file is read. An empty `COFFER_URL` is ignored. A bad `--url`, `COFFER_URL` or config URL exits 2: it must be http(s) with a host, and credentials, a query or a fragment are rejected.**
92. **`logout`: a 401 still removes the local token and exits 0. A network error or 5xx keeps the token (it may still be valid on the server) and exits with the mapped code. With no stored token it prints `not logged in` and exits 0. With `COFFER_TOKEN` set, it only calls the server.**
93. **Redirects are never followed, even when no Authorization header is set; any 3xx exits 1. Requests time out after 30 s, and response bodies are capped at 64 MiB.**
94. **`coffer --json secrets export --format dotenv` prints one JSON document, `{"content":"<dotenv text>","format":"dotenv"}`, with the dotenv body byte for byte in `content` (SPEC §7.1: `--json` prints exactly one JSON document). Without `--json`, dotenv goes to stdout raw. A json export is printed as the server sent it, with a trailing newline.** A body that isn't valid UTF-8 (which can't happen for SPEC-conformant values) exits 1 with nothing on stdout, rather than altering bytes.
95. **With `--json`, most commands print the server's response body re-indented, keeping its key order and values. The exceptions: login (token removed), 202 writes (`{"status":"pending","change_id"}`), and logout and version (documents the CLI builds).**
96. **Errors always go to stderr as `error: <message> (<code>)`. With `--json`, the CLI also writes `{"error":{"code","message"}}` to stderr, with the server's `code` and `message` unchanged (no `(<code>)` suffix). The CLI's own error codes are `usage`, `validation`, `connection`, `unauthenticated`, `not_found` and `error`; a server error with no code becomes `http_<status>`.** stdout stays empty when a command fails.
97. **Control characters, bidi overrides and invalid UTF-8 in text from the server are escaped in human output, error messages and tables. Secret values from `get` and export are never altered.** This blocks terminal escape injection through audit targets or emails.
98. **`login` warns on stderr when it sends credentials over plain HTTP to a host that isn't loopback. Reading a config file with looser mode than 0600 prints a warning, and the next write fixes the modes.**
99. **`login` rejects a returned token that doesn't start with `cof_pat_`, and `token create` one that doesn't start with `cof_st_` (exit 1). `token create` prints the token alone on stdout, and `id:` and `expires_at:` on stderr.** `TOKEN=$(coffer token create ...)` captures exactly the token.
100. **Extra commands: `help [COMMAND]`, `version`, `--help` and `-h`, all exiting 0. No arguments at all exits 2. On a terminal, `secrets set KEY` without a value prints a "Ctrl-D" hint on stderr.**

## Later additions: operations

101. **Script-only variables, documented in `.env.example` but never read by the server: `COFFER_COMPOSE`, `COFFER_CONTAINER_RUNTIME`, `COFFER_READY_TIMEOUT`, `COFFER_BUILD_IN_CONTAINER`, `COFFER_TEST_IN_CONTAINER`, `COFFER_TEST_DATABASE_URL`, `COFFER_E2E`, `COFFER_SMOKE_PORT`, `COFFER_SKIP_CLI_BUILD`.** Compose is detected in this order: `docker compose`, `podman compose`, `docker-compose`, `podman-compose`. The runtime for one-off containers prefers podman.
102. **`scripts/check-env-docs.sh` (in the CI lint job) enforces SPEC §5's "all documented in .env.example". `scripts/ops-smoke.sh` (in the CI e2e job) runs a private compose project to test env-change propagation, rotation, down/up and backup/restore.** Both are guards against drift that a reviewer would otherwise catch only by hand.
103. **The server image has no explicit `image:` name (compose picks the name), and `restart: unless-stopped` with a 10 s `stop_grace_period` on the server. The server shuts down within 8 s (`http.Server.Shutdown`).** SIGTERM always fits inside compose's grace period.

## Later additions: round-2 hardening

104. **Mutating org-scoped requests re-authorize the caller under a lock.** The org row serves as the per-org authorization lock. Member, role and grant changes take it `FOR NO KEY UPDATE`. Approve and reject, token issue and revoke, project and env create, secret writes and change proposals take it `FOR SHARE`. Org disable takes it `FOR UPDATE`. With the lock held, the server re-reads the org's disabled flag and the caller's token row (`FOR SHARE`), then decides using the caller's current role, grant and access. So an action ordered after a committed demotion, removal, grant change, token revocation or org disable is judged against the new state (SPEC §2.2, §2.9, §2.11). Responses:
    - Caller gone, token revoked, or org disabled: 401.
    - Caller lost the needed role: audited 403.
    - Writer whose grant was revoked: 404.
    - Writer whose grant was lowered: 403.

    Lock order is always: org row, caller's token row, change / target user / grant rows, secret rows, audit chain head.
105. **Approval re-checks the proposer.** The proposer must still be in the org with owner/admin or a writer grant, or, for a token, still be an unrevoked, unexpired read-write service token scoped to that project and environment. Otherwise the change becomes `stale` (409, audited `change.stale` with reason `proposer_unauthorized`). Role and grant are read in separate locking statements, so a concurrent revoke can't be missed. Losing write access is a "revocation" under SPEC §2.11, and it must not be bypassed by a change proposed earlier.
106. **An environment holds at most 10,000 live keys.** A set or rollback that would push it past that returns 409. Updates to existing keys and deletes are never capped. Versions per key are uncapped, because a cap would make a key permanently unwritable. Export and version history are streamed in batches of 256: each batch is decrypted, audited and committed before it is written. If a failure happens after the first batch has been sent, the connection is aborted rather than sending a body that looks complete. SPEC's performance target is 1,000 keys, so 10,000 leaves 10x headroom and bounds memory and response size.
107. **The P1 forced password change ships disabled (`COFFER_REQUIRE_PASSWORD_CHANGE=false`); see decision 35.** It is fully implemented and tested (`TestMustChangePassword`). Turning it on by default would make every freshly added member get 403 until they call `coffer passwd`. That would break any client that follows the documented flows (add a member, then work as that member) to gain a stretch goal. Operators who want the rule set the variable to `true`.
